1

인덱스란 무엇인가?

인덱스는 책의 목차와 같습니다. 책에서 원하는 내용을 찾을 때 처음부터 전부 읽는 대신 목차로 바로 페이지를 이동하듯, DB도 인덱스를 통해 데이터를 빠르게 탐색합니다.

인덱스 없음 (Full Table Scan)
┌─────────────────────────────────────────────┐
│  row1 → row2 → row3 → ... → row1,000,000   │  모든 행 순차 탐색
└─────────────────────────────────────────────┘

인덱스 있음
┌──────────────┐     ┌─────────────────────┐
│   Index      │────▶│  해당 행으로 바로 이동  │  O(log n)
└──────────────┘     └─────────────────────┘
구분인덱스 없음인덱스 있음
탐색 방식Full Table ScanB-Tree 탐색
시간 복잡도O(n)O(log n)
쓰기 속도빠름인덱스 갱신 비용 발생
저장 공간테이블만테이블 + 인덱스
트레이드오프 주의
인덱스는 읽기 성능을 높이기 위해 쓰기 성능과 저장 공간을 일부 희생하는 트레이드오프입니다. 남용하면 오히려 전체 성능이 떨어집니다.
2

인덱스 내부 구조 — B-Tree

대부분의 DB는 B-Tree(Balanced Tree) 구조로 인덱스를 구현합니다. 항상 균형을 유지하기 때문에 어떤 데이터를 찾아도 탐색 깊이가 일정합니다.

                    [  50  ]                  ← 루트 노드
                 ╱            ╲
         [ 20, 30 ]          [ 70, 80 ]         ← 브랜치 노드
        ╱    │    ╲          ╱    │    ╲
    [10]  [25]  [35]    [60]  [75]  [90]  ← 리프 노드 (실제 데이터 위치)

루트에서 시작해 값을 비교하며 내려가고, 리프 노드에서 실제 행의 위치(Row ID)를 얻어 테이블로 이동합니다.

3

단일 인덱스 vs 복합 인덱스

SQL
-- 단일 인덱스: 컬럼 1개
CREATE INDEX idx_email ON users(email);

-- 복합 인덱스: 컬럼 2개 이상
CREATE INDEX idx_name_age ON users(name, age);

복합 인덱스 (name, age)는 name으로 먼저 정렬하고, 같은 name 안에서 age로 정렬됩니다.

복합 인덱스 (name, age) 의 정렬 구조

  [Alice, 20]
  [Alice, 25]
  [Alice, 30]  ← name이 같으면 age 순 정렬
  [Bob,   22]
  [Bob,   28]
  [Carol, 19]
4

복합 인덱스 설계 원칙

복합 인덱스에서 가장 중요한 규칙은 Left-most Prefix Rule (선두 컬럼 규칙)입니다. 첫 번째 컬럼이 WHERE 조건에 없으면 인덱스를 사용하지 못합니다.

SQL — INDEX (user_id, status, created_at)
✅ WHERE user_id = 1
✅ WHERE user_id = 1 AND status = 'paid'
✅ WHERE user_id = 1 AND status = 'paid' AND created_at > '2024-01-01'
❌ WHERE status = 'paid'                          -- 선두 컬럼 없음
⚠️ WHERE user_id = 1 AND created_at > '2024-01-01'  -- user_id만 활용

컬럼 순서 결정 기준

1. = 조건 컬럼을 앞에  →  범위 조건( <, >, BETWEEN )은 뒤에
2. 카디널리티 높은 컬럼을 앞에  →  고유값 많을수록 더 잘 걸러냄
3. 자주 함께 쓰이는 컬럼끼리 묶기

✅ 좋은 순서:  INDEX (user_id, created_at)
   WHERE user_id = 1 AND created_at > '2024-01-01'

❌ 나쁜 순서:  INDEX (created_at, user_id)
   → 범위 조건 이후 컬럼은 인덱스 활용 불가
5

커버링 인덱스

쿼리에 필요한 모든 컬럼이 인덱스 안에 포함되어 실제 테이블을 전혀 조회하지 않아도 되는 인덱스입니다. 복합 인덱스의 한 형태입니다.

일반 인덱스

① 인덱스 탐색
↓
② Row ID 획득
↓
③ 테이블 접근 (I/O 발생)

커버링 인덱스

① 인덱스 탐색
↓
② 필요한 컬럼이 모두 인덱스 안에 있음 → 끝!
SQL
CREATE INDEX idx_covering ON users(name, age, email);

✅ 커버링 인덱스 적용 — SELECT 컬럼이 모두 인덱스 안에 존재
SELECT name, age, email FROM users WHERE name = 'Alice';

❌ 커버링 인덱스 불가 — address 는 인덱스에 없음
SELECT name, age, email, address FROM users WHERE name = 'Alice';

실행 계획에서 Extra: Using index 가 표시되면 커버링 인덱스로 동작 중입니다.

주의
커버링 인덱스는 포함 컬럼이 많아질수록 인덱스 크기가 커지고 쓰기 비용이 증가합니다. 자주 실행되고 성능이 중요한 쿼리에만 선택적으로 적용해야 합니다.
6

실행 계획 (EXPLAIN)

실행 계획은 DB가 쿼리를 어떻게 실행할지 보여주는 청사진입니다. 느린 쿼리의 원인을 정확히 진단할 수 있습니다.

SQL
EXPLAIN SELECT * FROM users WHERE email = 'test@example.com';
EXPLAIN ANALYZE SELECT * FROM users WHERE email = 'test@example.com';

type 컬럼 — 가장 중요한 지표

type의미성능
constPK/Unique로 1건 조회최상
eq_refJOIN에서 PK/Unique 1건 매칭매우 좋음
ref인덱스로 여러 건 조회좋음
range인덱스 범위 스캔보통
index인덱스 풀스캔나쁨
ALL테이블 풀스캔최악

Extra 컬럼 해석

Extra의미평가
Using index커버링 인덱스 사용최상
Using whereWHERE 필터링 발생보통
Using filesort정렬을 인덱스 없이 처리나쁨
Using temporary임시 테이블 생성나쁨

실전: 문제 진단 → 인덱스 추가 → 개선 확인

EXPLAIN 결과 비교
-- 인덱스 없을 때
| type | key  | rows  | Extra                       |
| ALL  | NULL | 95000 | Using where; Using filesort |
  ↑ 풀스캔!                          ↑ 정렬도 느림!

-- CREATE INDEX idx_user_created ON orders(user_id, created_at); 후
| type  | key              | rows | Extra         |
| ref   | idx_user_created |   10 | Using index   |
  ↑ 인덱스 사용!              ↑ rows 95,000 → 10!
실행 계획 체크리스트
type=ALL이면 위험 · key=NULL이면 인덱스 미사용 · rows가 크면 비효율 · filesort/temporary면 개선 필요
7

인덱스 종류 관계 정리

커버링 인덱스는 별도의 종류가 아니라, 복합 인덱스가 쿼리를 완전히 커버하는 상태를 말합니다.

인덱스
├── 단일 인덱스 컬럼 1개 · 기본 형태
└── 복합 인덱스 컬럼 2개 이상
└── 커버링 인덱스 SELECT 컬럼까지 모두 포함한 상태 (복합의 특수 케이스)
구분핵심 목적설계 부담
단일 인덱스특정 컬럼 검색 최적화낮음
복합 인덱스여러 조건 동시 최적화중간
커버링 인덱스테이블 접근 자체를 제거높음

세 가지는 경쟁 관계가 아닌 단계적으로 적용하는 최적화 도구입니다. 단일/복합으로 WHERE 조건을 최적화한 뒤, 필요할 때 커버링 인덱스로 발전시키는 것이 올바른 접근입니다.

8

인덱스를 걸어야 할 때

인덱스는 데이터 건수보다 카디널리티와 조회 패턴이 더 중요합니다.

데이터 건수별 인덱스 효율

  ~1,000건          인덱스 거의 의미 없음. 풀스캔이 더 빠름
  1,000 ~ 10,000건  애매한 구간. 쿼리 패턴에 따라 다름
  10,000건 이상     인덱스 효과가 본격적으로 나타남
  100,000건 이상    인덱스 없으면 체감상 느려짐
  1,000,000건~      인덱스 필수

데이터가 적은 테이블에서 인덱스를 자제하는 이유

풀스캔 (순차 I/O)
  [데이터] → 한 번에 쭉 읽음 → 빠름

인덱스 탐색 (랜덤 I/O)
  [인덱스 탐색] → [Row ID 획득] → [테이블 이동]
  단계가 더 많음 → 데이터가 적으면 오히려 느림

결론: 옵티마이저는 데이터가 적으면 인덱스가 있어도 무시하고 풀스캔 선택

카디널리티 — 건수보다 중요한 지표

예시
❌ 카디널리티 낮음 → 인덱스 효과 없음
  gender: M / F  (전체의 50%씩 — 너무 많이 조회됨)

✅ 카디널리티 높음 → 인덱스 효과 극대화
  email: 모든 행이 고유 (0.0001%만 조회)

-- DB 옵티마이저는 전체의 10~20% 이상 조회 시 인덱스를 무시함

실무 판단 순서

1. 인덱스 없이 운영 시작
↓
2. Slow Query Log 으로 느린 쿼리 감지
↓
3. EXPLAIN 으로 풀스캔 여부 확인
↓
4. 그때 인덱스 추가 ← 이것이 실무 정석
핵심 원칙
인덱스는 미리 설계하는 것보다, 느려진 걸 확인하고 나서 추가하는 것이 올바른 접근입니다.
💡
핵심 요약
· 인덱스 = 책의 목차. 읽기↑, 쓰기↓ 트레이드오프
· 단일 인덱스 → 복합 인덱스 → 커버링 인덱스 순으로 단계적 최적화
· 커버링 인덱스는 복합 인덱스의 특수 형태 (SELECT를 완전히 커버)
· 복합 인덱스는 선두 컬럼 규칙이 핵심 (= 조건 앞에, 범위 조건 뒤에)
· 데이터 적은 테이블 + 카디널리티 낮은 컬럼 → 인덱스 효과 없음
· EXPLAIN으로 type=ALL, filesort 를 잡아내는 것이 최적화의 시작
· 인덱스는 미리 만들지 말고, Slow Query 확인 후 추가하는 것이 정석
